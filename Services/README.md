# Services

Generally, tasks are launched within the jail from the host or from the jail itself, but they always run within the jail. Occasionally, tasks must be launched from the jail to the host. For example, opening a URL from an application within a jail to launch a web browser within another jail.

The host is used as an intermediary to utilize the wrapper (`${X11APPJAIL_APPDIR}/START`), since it may contain parameters necessary to run the application within the target jail, and failing to define those parameters may alter the application’s behavior. An alternative implementation involves communicating between jails point-to-point, but since there is no way to leverage what the wrapper currently does, the only way for this to work is to rewrite a similar wrapper from scratch but within the jail, which is unfeasible.

To use a service, at least two environment variables are required: `X11APPJAIL_SERVICE` and `X11APPJAIL_SERVICE_FROM`. The first specifies the service to be run, and the second indicates where that service will be provided. `X11APPJAIL_SERVICE_FROM` must be specified using the syntax `<APP>[:<PROFILE>]`. The installed wrapper must be run using these required environment variables, rather than from the binary used to install AppScript, in order to honor the environment variables set during installation.

Once the necessary environment variables have been set, The AppScript will simply run the service, which means it will install an "agent," an executable file located within the target jail’s data directory, specifically at `${X11APPJAIL_DATA}/x11appjail-<APP>-<UID>_<PROFILE>/.x11appjail/services/`. After the agent is installed, if `${X11APPJAIL_SERVICE}/agent.desktop` exists, it will be copied as `${X11APPJAIL_DATA}/x11appjail-<APP>-<UID>_<PROFILE>/.local/share/applications/x11appjail-${X11APPJAIL_SERVICE}.desktop`. Next, if the executable file `${X11APPJAIL_SERVICE}/post` exists, it will be executed with the `JAIL` environment variable set, which is the same as that of the jail in which the service will be provided. Finally, the AppScript, or, more specifically in this case, [service.sh](service.sh), will run `sysutils/unixexec` to create a `unix(4)` socket named `${X11APPJAIL_DATA}/x11appjail-<APP>-<UID>_<PROFILE>/.x11appjail/services/${X11APPJAIL_SERVICE}/sock`. When the agent connects to this socket, `${X11APPJAIL_SERVICE}/exec` is executed, attaching its stdout and stdin, so that the jail will see the output and can send data to the command’s stdin, just as if the command were running locally. `${X11APPJAIL_SERVICE}/exec` runs only when the other peer connects to the `unix(4)` socket, after which unixexec terminates; however, the current implementation rerun unixexec indefinitely unless `${X11APPJAIL_SERVICE}/exec` exits with a non-zero exit code or you terminate it explicitly.

However, a service should be kept as minimal as possible, and if it executes other commands, it should do so as a user other than the current one. And if the service displays a user interface, such as a dialog box, and the text is based in part on what passes through the jail, you must keep in mind that there are Unicode characters that are used by social engineering attacks, since they are invisible in their display but, once they reach the final destination, could compromise that target; therefore, you must make those characters human-readable.
